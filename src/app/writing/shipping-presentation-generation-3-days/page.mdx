# Building HarborCore: When Two People Change the Same Number

*Concurrency, database locking, and the surprisingly hard problem of keeping numbers honest.*

I built HarborCore because I wanted to understand what actually happens when multiple people try to change the same piece of data at the same time.

On paper, it sounds simple. You have a database, some transactions, and a dashboard sitting on top of it. A user makes an update, the database saves it, and everyone moves on.

But what happens when two users make conflicting updates simultaneously?

That was the question behind HarborCore.

I wanted to build something where concurrency wasn't just a word in a systems textbook. I wanted to actually see what goes wrong when you let competing transactions touch the same records—and then figure out how to make those failures impossible.

## The Problem

Imagine a system where several stakeholders can modify the same records.

User A reads a value.

User B reads the same value.

User A makes an update.

User B makes an update based on the old value.

Both transactions succeed.

The database is perfectly happy.

Your numbers are now wrong.

This is the kind of bug that makes an application look completely functional while quietly corrupting the data underneath it.

So I decided to build HarborCore around a simple requirement:

**If two people are trying to change the same record, the database should decide who gets to go first.**

## The Plan

The project had two parts.

First, I needed a reliable transactional backend that could handle concurrent updates without corrupting records.

Second, I wanted an analytics layer that could answer meaningful questions about the data without forcing the application to do all of the computation itself.

The second part turned out to be particularly interesting.

Instead of pulling thousands of rows into Python and calculating everything there, I wanted the database to do what databases are good at: filtering, joining, grouping, and aggregating data.

That meant getting much more comfortable with SQL.

## Making Concurrency Boring

The most important decision in HarborCore was pessimistic locking.

I used `SELECT FOR UPDATE` inside database transactions to lock rows before modifying them.

The idea is simple:

1. Start a transaction.
2. Find the record we want to modify.
3. Lock that record.
4. Make the update.
5. Commit the transaction.
6. Let the next transaction continue.

Now, if two users try to modify the same record simultaneously, they don't both get to pretend they were first.

One transaction gets the lock.

The other waits.

It sounds almost trivial when written like that. But actually reasoning about concurrent state was one of the most interesting parts of the project.

## Why Not Just Do It in Python?

At first, it is tempting to pull the data into Python and calculate everything there.

It works.

Until you have a lot of data.

Then you're moving rows from the database to the application, processing them, and potentially moving results back again.

I started pushing more of the analytical work into SQL instead.

CTEs made it possible to break complicated queries into readable stages. Window functions let me calculate rankings and running statistics without collapsing rows. Joins let me combine information across different parts of the system without manually stitching everything together in application code.

The database became more than a place where I stored data.

It became part of the computation.

## The Dashboard

I built the interface with Streamlit so I could focus on the underlying system rather than spend weeks building a frontend.

The dashboard exposes the results of the transactional and analytical layer in a way that makes the system easier to reason about.

More importantly, it gave me a way to actually test whether the decisions I made underneath the UI were producing sensible results.

## What I Learned

The biggest thing HarborCore taught me is that databases are not passive storage.

They're responsible for maintaining the truth of your application.

Concurrency makes that responsibility much more obvious. If you don't explicitly think about what happens when two things occur at the same time, your application will happily make assumptions for you—and those assumptions won't necessarily be correct.

I also came away with a much better appreciation for SQL.

I used to think of SQL mostly as a way to retrieve data.

HarborCore made me think about it as a computational tool: CTEs for structure, window functions for context, joins for relationships, and transactions and locks for correctness.

The project started with a fairly simple question:

**What happens when two people try to change the same thing?**

The answer, it turns out, is a lot more interesting than I expected.
